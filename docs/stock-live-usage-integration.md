# Live usage → stock delivery

Phase 3/Gate 1 technical records remain authoritative and unchanged. The stock AFTER INSERT triggers on `live_usage` and `live_material_reconciliations`, and terminal Live transition trigger, enqueue source component events in the same technical transaction. They do not wait for item/lot balance locks or a network response. A rolled-back technical save cannot leave a stock event; a committed save cannot lose its outbox record.

Stock consumption is the prepared raw component, including material later wasted. Existing verified 1:1 recipes supply two raw components. Original `live_usage.prepared_grams` is already per component. Gate 1 reconciliation prepared grams is total mixture, so each component is half that total. No second waste deduction is written. Planned recipe or bowl grams are never used as measured inventory facts.

For a session/bowl/product, the consumer follows the immutable reconciliation chain to its unsuperseded leaf. If none exists, it reads original authoritative usage. It computes `delta = prior applied component consumption - latest measured component consumption` and appends only that delta. A 60g mixture consumes 30g color and 30g developer; correction to 80g consumes 10g more of each; correction to 20g restores 30g of each. Existing original and correction rows are preserved. Delayed/reordered deliveries re-read the current leaf under the item lock, so they do not sum superseded measurements.

UNKNOWN is null, not zero. Terminal bowls without a measured preparation produce STOCK_USAGE_RECONCILIATION_REQUIRED. Measured zero can resolve usage to zero through an append-only positive correction. Missing verified mapping, missing opening count, incompatible units, required lot or insufficient quantity produce FAILED with an explicit code. Source facts are retained. Delivery never rolls back or reopens a stopped technical session. Retrying an event uses a new attempt mutation; replaying an earlier failure mutation returns its permanent prior result.

Delivery executor: `node scripts/process-stock-outbox.mjs`. Run periodically on a server in Dev/Staging/Pilot with a dedicated authorized database membership. It signs in through Auth using a publishable key, posts a bounded PROCESS_BATCH (up to 20 PENDING events with SKIP LOCKED) and signs out locally. It uses no service-role key and never logs tokens, credentials or customer payloads. Configure `ELIFORA_STOCK_WORKER_URL`, `ELIFORA_STOCK_WORKER_PUBLISHABLE_KEY`, `ELIFORA_STOCK_WORKER_EMAIL`, `ELIFORA_STOCK_WORKER_PASSWORD`, `ELIFORA_STOCK_WORKER_MEMBERSHIP`, `ELIFORA_STOCK_WORKER_LOCATION` and `ELIFORA_DEPLOYMENT_ENV` in the executor's secret store. Never commit those values. No external environment is provisioned or scheduled by this development slice.

PENDING → PROCESSED/FAILED transitions, attempts and error codes are durable. Operator retry in the stock Action Center resolves FAILED delivery after factual mapping, lot, receipt or technical reconciliation changes. The server worker handles PENDING events independently of browser rendering; the browser is neither the event producer nor the reliability mechanism. Historical FAILED event receipts remain reproducible even after a later attempt succeeds.

Stock availability is read-only and follows verified technical selection. OUT_OF_STOCK warns the professional; it does not choose a different system/developer, lower the safety gate, regenerate pigment facts, reserve stock or write a cost relation. The only trusted appointment relation is `salon_appointment_live_links`; legacy Live payload UUIDs are ignored. Client merges do not rewrite movement/session attribution.

Gate 1 already rejects a measured 20.01 g 1:1 reconciliation because its 10.005 g component cannot be represented in 0.01 g minor units. That existing rule is preserved; a rejected technical update leaves no stock outbox event. The stock consumer also checks component precision defensively and never rounds an unrepresentable source. A valid 20.02 g mixture yields exact 10.01 g components.
